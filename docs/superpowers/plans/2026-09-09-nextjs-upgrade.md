# Next.js/React/Vitest Major-Version Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close all 6 `npm audit` findings in `frontend/` by bumping Next.js, React, and the Vitest/Vite test toolchain across their major versions, staged so any breakage stays traceable to exactly one package.

**Architecture:** Five sequential tasks, each its own commit, each gated by a green test/build check before the next begins: test-tooling (fully decoupled from Next/React) → Next.js 16 (React stays on 18.3, since `next@16` supports both 18.2+ and 19, but `next@14` only supports 18.2+ — this ordering is what avoids a peer-dependency conflict) → React 19 (now safe, since Next already accepts it) → a production build driven through the full Playwright E2E suite as the real safety net (no staging environment exists) → a final audit-closure check.

**Tech Stack:** Next.js, React, Vitest/Vite, TypeScript, Playwright — all in `frontend/`.

## Global Constraints

- DCO `Signed-off-by` (via `git commit -s` — the human's identity is already configured in git, never type a literal placeholder line) + Conventional Commits + a separate `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>` trailer on every commit.
- No new Next.js features: no Server Actions, no `next/image`, no new Middleware logic. This plan is version bumps only.
- `output: "standalone"` must remain set in whichever `next.config` file exists at the end (ADR-010).
- `frontend/src/middleware.ts` (the anonymous-id cookie) must remain behaviorally unchanged — re-verify it still works, never modify its logic.
- `frontend/README.md`'s BFF conventions (session-cookie handling, the Google OAuth redirect-URI convention) are out of scope — do not touch anything there.
- No license headers needed — this plan creates no new files.
- Each task is its own commit; a task that breaks something must be revertible without touching the others.
- This is a dependency-upgrade plan: most steps are "bump to an exact version, run the gate, fix whatever real failure the gate reveals, re-run until green." No task can enumerate every possible break a major version bump might cause in advance — where a step says "fix any real failures," that is deliberate, not a placeholder: the fix itself must still be a real, working change verified by a green re-run, never a skipped/loosened assertion.

**Files:**

If it finds a real regression, the fix belongs in whichever of Tasks 1-3 introduced it (reopen that task's commit with a fixup, per this plan's own "each task must be independently revertible" constraint — do not silently patch the regression inside this task's own, otherwise source-code-free, commit).

**Interfaces:**
- Consumes: Tasks 1-3's fully upgraded stack.
- Produces: proof, via a real production build and a real browser driving real backend services, that the upgrade works end-to-end — not just per-package. Since this repo has no staging environment, this task IS the safety net this plan's spec calls for.

The 4 existing spec files (`tests/e2e/search-and-browse.spec.ts`, `tests/e2e/chat-and-history.spec.ts`, `tests/e2e/account-management.spec.ts`, `tests/e2e/accessibility.spec.ts`) exercise real page flows against real backend data, not mocks — they need the actual `accounts`/`api`/`chat` services and Postgres running and reachable at whatever URLs `frontend/`'s own env config points at (check `frontend/.env.local` or equivalent for the exact expected backend URLs before starting the services).
